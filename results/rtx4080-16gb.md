## 속도

다른 프로그램을 모두 끈 상태 기준이다.

| 항목 | 값 |
|---|---|
| 생성 속도 | 41.0 tok/s |
| 프롬프트 처리 | 820~848 tok/s |
| 500토큰 생성 | 12.2초 |
| 모델 로딩 | 4.1초 |
| VRAM 점유 | 15.2 / 16.4GB, 100% GPU |

GPU를 쓰는 프로그램을 띄워둔 채로도 24K는 100% GPU를 유지했지만 느려졌다.

| 상태 | VRAM 여유 | 생성 | 프롬프트 처리 |
|---|---|---|---|
| Chrome·Discord·Codex 실행 중 | 12.8GB | 37.8 tok/s | 265~292 tok/s |
| 전부 종료 | 15.4GB | 41.0 tok/s | 820~848 tok/s |

프롬프트 처리가 3배 차이 난다. 긴 파일을 붙여넣을 때 체감이 크다.

## context 한계선

| context | 배치 | 생성 속도 |
|---|---|---|
| 16K | 100% GPU | 37.6 tok/s |
| 20K | 100% GPU | 37.8 tok/s |
| **24K** | **100% GPU** | **41.0 tok/s** |
| 28K | 6% CPU / 94% GPU | 29.0 tok/s |
| 32K | 7% CPU / 93% GPU | 27.4 tok/s |
| 40K | 9% CPU / 91% GPU | 25.2 tok/s |

24K와 28K 사이가 절벽이다. VRAM이 6GB 남는 상태에서 32K를 시도해도 결과는 같았다. Ollama가 계산 버퍼용 여유를 따로 잡기 때문이라 VRAM을 비운다고 해결되지 않는다.

## 코딩 벤치마크

`bench/run.py`로 측정했다. 모델이 내놓은 코드를 파일로 저장한 뒤 실제로 실행해 숨긴 테스트를 통과하는지 본다.

| 설정 | 통과 | 문제당 평균 |
|---|---|---|
| thinking ON | 9 / 10 | 30초 |
| thinking OFF | 6 / 10 | 9초 |
| qwen3:4b (대조군) | 2 / 10 | 25초 |

통과한 문제들: LRU 캐시, 최장 유효 괄호, 두 정렬배열 중앙값 O(log), 이진트리 직렬화, k회 주식거래 DP, 정규식 매칭, 위상정렬, word break 전체해, 스레드 안전 RateLimiter.

중앙값 문제는 랜덤 200케이스 교차검증을 통과했고, RateLimiter는 5스레드 100회 동시 호출에서 정확히 50개만 허용했다.

### 실패한 문제

정수 계산기 파서(단항 마이너스 포함) 하나가 실패했다. 원인이 특이하다. thinking이 끝나지 않았다.

- 4,096토큰 한도: thinking 15,699자 쓰고 잘림, 답변 0자
- 12,000토큰 한도: thinking 42,940자 쓰고도 미완, 304초 소모
- thinking OFF: 41초 만에 통과

`--5` 같은 중첩 단항 연산자 엣지 케이스에서 결론을 못 내고 자기 검증을 반복했다. 상용 모델에서는 보기 드문 실패 방식이다. 같은 설정에서 한 번은 통과하고 한 번은 실패해, 경계에 걸친 문제로 보인다.
